Read this first. Shader Protocol is an early-stage, open-source research project. It runs on developer networks (devnets/testnets) only. The code has not been audited. Its zero-knowledge proving keys come from a single-party development trusted setup that is not secure for real value. A multi-party ceremony has not been started. Parts of the system (adapters other than the first EVM/Solana paths, live message transports, on-chain allowance verification) are incomplete. There is no token, no token sale, no mainnet deployment and no partnership with any chain, exchange or broker named here. Nothing here is financial, legal or tax advice.

01 // THE PROBLEM

Public ledgers leak too much.

Public blockchains give verifiability. The price is that balances, counterparties, order flow and strategy are visible to everyone, forever.

  • Balances are public. Wallet identity links to every inflow and outflow.
  • Orders are public before they execute. Pending trades in public mempools invite copy and sandwich flow.
  • Front-running and MEV follow. Extractable value comes from reading intent before settlement.
  • Counterparties and strategies leak. DAOs, desks and agents cannot keep commercial detail private by default.

Centralized venues and naive mixers are unsatisfying. Shader Protocol aims for private-by-default execution with optional, deliberate disclosure.

02 // OVERVIEW

The idea in one paragraph.

Shader Protocol is a shielded execution layer. Users hold value as encrypted notes inside a shielded pool, move it with Groth16 / Circom proofs that show a transaction is valid without revealing who, what or how much, and can trade through a dark pool where orders stay sealed until match and settlement. Notes carry an asset id and a chainHome so a note minted on one chain does not open on another unless a teleport mints it there. On top sit selective-disclosure tools (viewing keys, scoped bundles, issuer-signed credentials, regulator capabilities), agent allowance notes, private payroll batches, and ERC-20 deposits on the EVM pool. The core is chain-agnostic; thin adapters target listed testnets only.

03 // NOTES v2

Commitments that know their home.

Devnet note format. Not audited. Not for mainnet. A note opening is:

FieldMeaning
value64-bit amount
blinding, rhoSecret field elements. Deposit rho is chosen by the depositor. Spend outputs derive rho from the input nullifier.
ownerPoseidon(owner domain, spending key)
assetIdAsset identifier
chainHomeChain that minted the note

Asset and chain are domain-tagged, then packed, so every chain uses the same 6-input commitment:

assetTag   = Poseidon(7, assetId)
chainTag   = Poseidon(9, chainHome)
packed     = Poseidon(assetTag, chainTag)
commitment = Poseidon(1, value, blinding, rho, owner, packed)

A note minted on Robinhood Chain testnet (46630) does not open on Elysium testnet (99801) unless a teleport mint inserts that commitment into the destination tree.

Nullifier binding. The nullifier is bound to the spending key, the commitment and the leaf index:

nullifier = Poseidon(2, spendingKey, commitment, leafIndex)
rhoOut    = Poseidon(6, nullifier, outputIndex)

Two notes that reuse rho no longer share a nullifier. Output rhos are derived; a spender cannot choose them freely.

extDataHash binding. Recipient, relayer, fee, pool and chain are bound into the public input so a proof for one pool cannot authorize a payout from another:

binder      = Poseidon(5, poolLo, poolHi, chainDomain, withdrawAmount, relayerFee)
extDataHash = Poseidon(recipientLo, recipientHi, relayerLo, relayerHi, binder, 0)

Shared circuit family (v2 commitment + same extDataHash): shielded_transfer.circom (1-in / 2-out withdraw), transfer.circom (2-in / 2-out), teleport_out.circom (burn one note; output commitment uses destChain as chainHome). Default npm run circuit:setup builds the withdraw circuit only. Transfer and teleport proving keys are not produced by that default run. The setup remains a single-party development setup.

04 // TELEPORT

Two transports. Per-epoch caps.

Cross-chain move of shielded value is a burn on the source tree plus an attested mint on the destination. The destination pool's mintAttested path accepts a commitment only after a message verifier confirms the payload.

Two-transport agreement. TwoOfTwoVerifier requires two independent transports to submit the same (destChain, commitment, nullifier, amount) body. A single transport is rejected. Hyperlane and LayerZero adapters in the repository are stubs marked NOT WIRED; tests use mock transports. The first designed lane is Robinhood Chain testnet (46630) to Kinetiq Elysium testnet (99801).

Per-epoch cap. Attestation consumes an epoch value budget. When epochUsed + amount would exceed epochCap, attestation reverts. Epoch boundaries follow block.timestamp / epochLength.

Canton is separate: it is not a Groth16 verifier. Daml has no BN254 pairing. Canton records a result only when two named attestors authorize it (2-of-N over the named set). If two attestors sign a result that never happened on the EVM pool, Canton records it. That is attestation, not proof verification. The TypeScript Canton adapter still throws NotImplementedError. Nothing is deployed to Canton DevNet from this repository.

05 // APPLICATIONS

Allowances, payroll, ERC-20.

Agent allowance notes. circuits/allowance_spend.circom and src/core/agent/allowance.ts bind a spend cap and expiry into the note commitment. The circuit checks amount <= cap, amount <= value and now <= expiry with 64-bit range checks. An x402-style helper builds a public payment object; it does not call a live x402 endpoint. The shielded pool does not yet verify allowance proofs on-chain. Witness tests cover over-cap and expired now.

Private payroll. src/core/payroll/batch.ts builds one stealth outgoing note per payee. chainHome is inside each commitment, so a payroll for one chain does not open on another.

ERC-20 support. The EVM pool can bind a mock or real ERC-20, accept depositToken, and pay recipient and relayer in that token on shieldedTransfer. The forge test testErc20DepositAndWithdrawPaysBothParties covers that path. Native and token modes are mutually exclusive per pool instance.

07 // DISCLOSURE

Private by default. Disclose by choice.

Selective-disclosure features are tools. Using them does not make any deployment or user compliant with any law. No regulator has reviewed or approved Shader Protocol.

  • Viewing keys decrypt notes for an address but cannot spend. Sharing a full viewing key is irreversible for past and future notes until the user moves address.
  • Scoped disclosure bundles (documented) limit reveal to a time range, asset or note set without handing over the full viewing key.
  • Regulator capabilities are issuer-signed encryption keys with a scope. Notes sealed to a capability use scope-bound AES-GCM associated data. Expired or re-scoped capabilities fail.
  • Credentials are Poseidon-hashed field records with an issuer Ed25519 signature over the hash. Presentations must match the issuer store. Self-asserted KYC levels are ignored.
  • No ZK disclosure proof yet. generateGroth16KycProof() throws NotImplementedError. There is no Groth16 selective-disclosure KYC circuit in the devnet artifact set. Disclosure receipts today are signature- and key-based, not zero-knowledge proofs.
  • Sanctions screening is an interface. DevnetPermissiveScreen does not check a list.
08 // CEREMONY & KEYS

Ceremony planned. Not yet run.

Keys from npm run circuit:setup are a single-party development setup. Toxic waste is not destroyed. Do not deploy those keys. Anyone who keeps the intermediate parameters can forge proofs.

Ceremony tooling lives under scripts/ceremony/. It reuses the pinned Hermez Powers of Tau file powersOfTau28_hez_final_16.ptau. Scripts refuse to run unless SHADE_CEREMONY_ACK=circuits-not-frozen is set. That flag means you are exercising tooling. It does not open a ceremony. The browser page website/ceremony.html is labelled "Ceremony not started" and does not accept contributions. No transcript is published under circuits/ceremony/published/.

A real ceremony needs frozen circuit source, a large enough ptau, at least one honest contributor who destroys entropy, and a beacon. None of that has started.
