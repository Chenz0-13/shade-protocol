Cryptography

Parameters below match the current devnet design. They can change. Nothing here has had an independent audit.

Notes

A commitment is a Poseidon hash of the note opening, so the value, the asset, and the owner are not written in the clear. The nullifier is bound to that commitment and to the leaf index. Spending the same leaf twice produces the same nullifier, and the pool rejects the second one.

External data

extDataHash is a public input. It binds the recipient, the relayer, the fee, the chain, and the pool. The contract recomputes the hash from the call it is actually executing. A proof that was built for a different recipient, fee, chain, or pool does not verify against that call.

The public inputs are canonical field elements. Callers do not pass raw byte strings into the verifier and hope the encoding matches.

Roots

The commitment tree is a Poseidon Merkle tree. The devnet depth is small on purpose so tests can run. Pools keep a root history. A proof must name a root that is still in that history, not an arbitrary hash.

Stealth and regulator keys

Stealth addresses are secp256k1. The sender uses the recipient's spend and view public keys to derive a one-time address. The view key recognizes that address and opens the ciphertext. It cannot derive the spending key the circuit checks. Poseidon is not homomorphic, so the curve key and the circuit spending key stay separate.

A regulator capability is an issuer-signed secp256k1 encryption key plus a scope. Notes sealed to it use associated data bound to that scope. A key for one scope does not open another scope. An expired capability fails.

Proofs

Proofs are Groth16. The keys in the repository come from a single-party development setup. They are not the output of a multi-party ceremony. Anyone who kept the intermediate parameters can forge proofs. Do not protect real value with them. A ceremony is planned, and it has not been run.
